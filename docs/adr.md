# LCM Graph Extra — 架构决策记录 (ADR)

> 记录关键架构决策及其背景、方案对比、后果。

## ADR-001: 四层检索引擎

**日期**: 2025-12  
**状态**: 已采纳

### 背景
Agent 需要从多个来源获取上下文信息：对话历史（lossless-claw）、代码/文档（QMD）、知识图谱（Neo4j）、经验教训（经验蒸馏）。单一来源不足以支撑高质量回复。

### 决策
采用四层检索架构，每层独立检索，由 Merger 统一去重和重排：

| 层 | 来源 | 检索方式 | 作用 |
|----|------|---------|------|
| L1 | lossless-claw DAG | FTS5 全文搜索 | 对话历史 |
| L2 | QMD | BM25 + 向量 + MCP | 代码/文档 |
| L3 | Neo4j 图谱 | Cypher 查询 | 实体关系 |
| L4 | 经验蒸馏 | 混合搜索 + 时间衰减 | 经验教训 |

### 替代方案
- **单层检索**：仅用 L1 或 L2，丢失图谱关系和经验记忆
- **全量注入**：每次注入全部上下文，导致 token 浪费和上下文污染

### 后果
- 正面：覆盖全面，支持多模态检索
- 负面：增加检索延迟（3-4 个并行请求），需要 Neo4j 基础设施

## ADR-002: 压力分级自适应

**日期**: 2026-01  
**状态**: 已采纳

### 背景
长期运行场景下，上下文窗口逐渐填满。需要根据当前压力自动调整检索量和注入量，避免 LLM 上下文溢出。

### 决策
三级压力模型，基于消息数和 token 占比自动分级：

| 等级 | 阈值 | 检索量 | 注入量 | compact 行为 |
|------|------|--------|--------|-------------|
| low | msg<=24, ratio<=0.70 | 全量 | 12000 chars | 不触发 |
| medium | msg<=48, ratio<=0.85 | 减半 | 6000 chars | 异步 |
| high | otherwise | 最小 | 1600 chars | 同步 |

### 替代方案
- **固定配置**：用户手动调参，增加运维负担
- **线性降级**：连续降级而非三级跳，体验不够平滑

### 后果
- 正面：自动适应，零运维干预
- 负面：阈值固定，无法针对不同 LLM 窗口大小动态调整

## ADR-003: MoA 多模型协作

**日期**: 2026-06  
**状态**: 已采纳

### 背景
单模型回复存在盲区（视角单一、缺乏批判性评估）。MoA（Mixture of Agents）通过多模型协作提升回复质量。

### 决策
两层架构：参考模型层（并行/串行多视角分析）+ 聚合模型层（批判性评估 + 综合）

- 参考模型：2-4 个，不同 system prompt 提供不同视角
- 聚合模型：1 个，批判性评估各参考模型输出，生成最终回复
- 复杂度门控：8 维度评分，仅高复杂度问题触发 MoA
- 预设系统：3 个默认预设 + 自动分类
- 工具调用：当前仅聚合模型有工具调用能力（架构限制）

### 替代方案
- **单模型循环**：多次调用同一模型，视角单一
- **投票机制**：多数投票决定最终输出，丢失批判性评估

### 后果
- 正面：多视角、批判性评估、高质量回复
- 负面：增加 3-5x LLM 调用成本，延迟增加 2-3x

## ADR-004: 上下文压缩委托

**日期**: 2026-03  
**状态**: 已采纳

### 背景
长期对话中，消息历史需要压缩为摘要注入 LLM 上下文。自研压缩算法复杂度高，且 lossless-claw 已提供成熟的 compact 能力。

### 决策
委托 lossless-claw 进行上下文压缩，而非自研压缩算法。

- 无损存储：原始消息始终在 DB 中，compact 只影响注入的 LLM 上下文
- 输入超限保护：当 `effectiveTokenCount > contextWindow * 0.90` 时跳过 compact，使用降级上下文
- 迭代压缩：一次 compact 不够时，链式触发第二次
- 异步回退：同步 compact 失败时，后台异步重试

### 替代方案
- **自研压缩**：完全控制压缩逻辑，但重复造轮子
- **无压缩**：长期运行必 OOM

### 后果
- 正面：复用成熟方案，减少维护成本
- 负面：依赖 lossless-claw 接口，黑盒委托不可控

## ADR-005: Dashboard 独立部署

**日期**: 2026-04  
**状态**: 已采纳

### 背景
需要可视化监控界面，但插件运行在 OpenClaw 宿主进程中，无法直接 serve 前端。

### 决策
Dashboard 独立部署为 Fastify 服务，通过 HTTP 与插件通信。

- 三层架构：插件 snapshot 服务 (:7423) → Dashboard 后端 (:7421) → 前端 (:7422)
- 解耦设计：插件不可用时，Dashboard 仍可通过 DB 直读展示历史数据
- 前端技术栈：Vue 3 + Naive UI + ECharts + TanStack Query

### 替代方案
- **内嵌 Web UI**：在插件进程中 serve 前端，耦合度高
- **CLI 工具**：仅命令行监控，可视化不足

### 后果
- 正面：解耦、独立部署、可视化丰富
- 负面：增加部署复杂度（3 个端口），需维护前后端通信
